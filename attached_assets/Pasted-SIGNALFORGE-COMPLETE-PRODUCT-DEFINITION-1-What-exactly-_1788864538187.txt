SIGNALFORGE — COMPLETE PRODUCT DEFINITION
1. What exactly are we building?

SignalForge is a multi-user SaaS platform for traders that transforms trading signals from external sources into a controlled, intelligent trading workflow.

The platform allows a user to:

Connect signal sources
        ↓
Receive messages
        ↓
Detect potential trading signals
        ↓
Extract structured trade information
        ↓
Analyze the signal with AI
        ↓
Evaluate provider/source reliability
        ↓
Validate the signal
        ↓
Detect duplicates/conflicts
        ↓
Apply user's trading rules
        ↓
Apply risk controls
        ↓
Choose Demo or Live account
        ↓
Execute through MetaApi
        ↓
Monitor the trade
        ↓
Record everything
        ↓
Analyze performance

The platform should support both:

Manual mode

The system analyzes the signal and presents it to the user.

Signal detected
      ↓
AI analysis
      ↓
Validation
      ↓
User sees:
BUY EURUSD
Entry: ...
SL: ...
TP: ...
Confidence: ...
      ↓
User decides
Automated mode

The system can execute an approved signal according to the user's configured rules.

Signal
 ↓
AI
 ↓
Validation
 ↓
Risk Engine
 ↓
Automation Rules
 ↓
Execution Engine
 ↓
MetaApi
 ↓
MT4 / MT5

Automation must never bypass the validation and risk layers.

3. Signal sources

The platform is designed to support multiple sources.

Primary source

Telegram User Session

This is the method we selected for Telegram.

A user connects their Telegram account/session to SignalForge and selects the channels/groups they want SignalForge to monitor.

User Telegram Session
        ↓
Selected Telegram Channels
        ↓
Message Listener
        ↓
SignalForge

The system should not simply treat every message as a trade.

For example:

"Good morning everyone"

is not a signal.

But:

EURUSD BUY
Entry 1.1050
SL 1.1020
TP 1.1110

is a potential signal.

Other source adapters

The architecture should support:

Telegram
Discord
WhatsApp where technically/legally supported
Email
TradingView
REST/API sources
Future custom providers

The important architectural principle is:

Telegram Adapter ──┐
Discord Adapter ───┤
Email Adapter ─────┤
TradingView ───────┤
REST API ──────────┤
                   ▼
            Unified Message
                   ▼
            Signal Pipeline

So the AI agent should not build the entire system specifically around Telegram.

Telegram is the first source adapter.

4. Provider concept

SignalForge needs a Provider concept.

A provider is the source/person/channel that generates signals.

For example:

Provider
   │
   ├── Name
   ├── Description
   ├── Source
   ├── Channels
   ├── Signal history
   ├── Accuracy statistics
   ├── Performance
   ├── Reputation
   ├── Number of subscribers
   └── Status

This creates the foundation for a future signal-provider marketplace.

Users can discover providers and decide which sources to connect/follow.

5. Provider DNA

One of the important AI components is Provider DNA.

SignalForge should learn the structure and behavior of each provider.

For example, one provider may normally send:

BUY EURUSD
ENTRY 1.1000
SL 1.0970
TP1 1.1030
TP2 1.1060

Another may write:

EUR/USD LONG @ 1.1000
Stop: 1.0970
Targets: 1.1030 / 1.1060

The Provider DNA layer learns:

terminology
formatting
symbols
entry conventions
stop-loss conventions
take-profit conventions
signal timing
historical behavior
provider reliability
typical signal quality

This makes signal extraction much more reliable.

7. Signal normalization

Different providers may express the same thing differently.

The system converts everything into one internal format.

For example:

BUY EURUSD NOW

becomes:

{
  "symbol": "EURUSD",
  "direction": "BUY",
  "entry_type": "MARKET"
}

Another:

EURUSD LONG @ 1.1050
SL 1.1020
TP 1.1100

becomes:

{
  "symbol": "EURUSD",
  "direction": "BUY",
  "entry": 1.1050,
  "stopLoss": 1.1020,
  "takeProfit": 1.1100
}

The entire platform works with the normalized representation.

8. Signal validation

Before a signal becomes executable, it goes through validation.

Validation can check:

Is the symbol valid?
Is the direction valid?
Is entry available?
Is SL available when required?
Is TP available when required?
Is the message actually a signal?
Is the signal expired?
Is the source trusted?
Is this a duplicate?
Does it conflict with another signal?
Is the market currently tradable?
Does it violate the user's rules?
Does the account permit the trade?
Does the risk calculation pass?

Only after validation can the signal continue.

9. Multiple messages and duplicate signals

This is one of the problems you identified earlier.

Suppose 500 users subscribe to the same Telegram channel.

The channel sends:

EURUSD BUY @ 1.1050

SignalForge should not process the message 500 times.

Instead:

Telegram
   ↓
ONE incoming message
   ↓
ONE normalized signal
   ↓
ONE AI analysis
   ↓
ONE validated signal
   ↓
Fan-out
   ├── User A rules
   ├── User B rules
   ├── User C rules
   └── User D rules

This is a critical architectural requirement.

The system needs:

Message ID

Identify the original message.

Signal fingerprint

Identify equivalent signals.

Idempotency

Prevent duplicate processing.

Fan-out

Deliver one validated signal to many subscribers.

10. Conflicting signals

Suppose:

Provider A:
EURUSD BUY

and shortly afterward:

Provider B:
EURUSD SELL

SignalForge shouldn't blindly execute both.

The system should detect the conflict and process it according to the configured consensus/decision rules.

Possible internal result:

EURUSD
────────────────
BUY providers: 4
SELL providers: 1

Consensus: BUY
Confidence: High

But the actual decision must still respect the user's rules and risk configuration.

13. Risk engine

The risk engine is one of the most important parts of SignalForge.

It determines whether an otherwise valid signal is allowed to reach execution.

Conceptually:

Signal
   ↓
User Account
   ↓
Risk Configuration
   ↓
Risk Calculation
   ↓
PASS / BLOCK

The engine should consider things such as:

account balance/equity
configured risk
stop-loss distance
symbol specifications
position size
existing exposure
open trades
daily limits
user-defined restrictions

The platform should fail closed: if a critical risk check cannot be completed reliably, the trade should not automatically execute.

14. Demo vs Live

We specifically discussed allowing the user to choose the account type.

The system should support:

DEMO

and

LIVE

A user should clearly see:

Current Trading Environment

● DEMO
○ LIVE

Live trading should require stronger confirmation and configuration than demo operation.

The UI must make the environment extremely obvious so a user doesn't mistake a demo connection for a live account.

15. MetaApi integration

MetaApi is the broker connectivity layer.

SignalForge doesn't directly communicate with MT4/MT5 terminals.

Instead:

SignalForge
     ↓

     ↓

     ↓
Broker

The backend stores each connected account's MetaApi account ID.

Example:

 ↓
broker_account

 ↓

The MetaApi token stays server-side only.

24. Referral system

We added this feature specifically.

Every user can have a referral code/link.

Example:

signalforge.com/register?ref=SF123456

The system records:

Referrer
     ↓
Referral
     ↓
Referred User
Your agreed reward model

The reward is not deducted from the referred user's trading earnings.

Instead:

The referral reward is paid from SignalForge's own platform income.

The reward is calculated based on the referred user's qualifying monthly earnings.

For example:

Referred user's qualifying monthly earnings:
$3,000

Referral percentage:
0.1%

Referral reward:
$3.00

So:

Referred user
     │
     └── continues trading normally

SignalForge platform revenue
     │
     ├── operating/platform income
     │
     └── referral reward allocation
                  ↓
              Referrer

The referred trader's account balance should not be reduced by the referral reward.

The system needs:

referral_code
referrer_id
referred_user_id
qualified_period
qualifying_earnings
reward_percentage
reward_amount
status
paid_at

The reward calculation should run through a controlled monthly settlement process with an auditable ledger.

46. Final product definition for the AI agent

You can give your coding agent this as the core instruction:

Build SignalForge as a production-grade multi-user SaaS trading signal intelligence and automation platform. SignalForge receives trading messages from connected external sources, beginning with Telegram User Sessions, detects and normalizes potential trading signals, uses AI and Provider DNA to understand and analyze them, validates signal quality, detects duplicates and conflicts, calculates confidence and consensus, and then applies each user's individual trading rules and risk controls. Only signals that pass all required checks can proceed to an execution request. Authorized execution requests are sent from the secure Express backend through MetaApi to the user's connected MT4/MT5 account. MetaApi account IDs are mapped to individual broker accounts in PostgreSQL, while MetaApi credentials remain server-side secrets. Real-time MetaApi events synchronize account, order and position state back into SignalForge.

The platform must support manual and automated trading modes, Demo and Live environments, multiple signal sources, multiple providers, provider reputation and Provider DNA, signal analytics, provider analytics, signal replay, certification, marketplace functionality, subscription plans, payments, KYC verification, referrals, notifications, audit logs, administration, security, and platform monitoring.

KYC is a mandatory access-control layer. Users must complete KYC before subscribing, activating protected functionality, accessing referrals, connecting/activating trading functionality, or performing other configurable protected actions. Users who are not verified must see a persistent account-verification status and be prompted to complete KYC.

The referral system uses a platform-funded reward model. The referred user's earnings are not reduced. At the end of each qualifying monthly period, SignalForge calculates the referral reward based on the referred user's qualifying monthly earnings using the configured referral percentage, initially 0.1%, and records the liability and settlement in an auditable referral ledger funded from SignalForge's platform income.

The platform must be event-driven and designed to process one incoming source message once and fan the resulting validated signal out to many subscribed users, with idempotency, duplicate detection, queues/workers, retries and per-user personalization. A single signal must never be unnecessarily reprocessed independently for every subscriber.

The frontend must never contain MetaApi secrets or privileged backend credentials. React communicates only with the SignalForge API. Express owns authentication, authorization, business logic, AI orchestration, risk controls, MetaApi integration, payment verification, KYC workflow, referral calculations, audit logging and execution orchestration. PostgreSQL is the primary persistent data store, with appropriate event/queue/cache infrastructure for asynchronous and real-time workloads.

Every critical action must be auditable. The system must be designed for production reliability, security, observability, graceful failure, idempotency, concurrency control, real-time updates and future horizontal scaling.
